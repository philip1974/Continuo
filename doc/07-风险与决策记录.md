# 07 · 风险与决策记录

## 已知风险

### R1 · Dockview 自带 popout 与 Electron BrowserWindow 冲突

**现象**：Dockview 的 popout 用 `window.open`，Electron 默认会打开新 BrowserWindow，但配置（preload、安全策略、尺寸）由 Chromium 默认值决定，我们拿不到控制权。

**影响**：popout 窗口里 `window.api` 是 `undefined`，无法读 layout，无法 IPC。

**缓解**：
- v1：保留 Dockview 自带 popout（仅主屏可用），通过 `app.on('web-contents-created')` 在 main 进程拦截新建的 webContents，强制把 preload 注进去。
- v2：完全接管，监听 Dockview 的 group location change，自己起 BrowserWindow（详见 `05-Electron-集成.md`）。

---

### R2 · `layoutId` 与 Dockview 内部 portal 冲突

**现象**：Dockview 内部用 React Portal 把 panel body 渲染到某个虚拟 DOM 节点，Motion 的 `layoutId` 跨 portal 时可能测不到正确尺寸。

**影响**：跨 group 的 `panel-title-${id}` shared layout 动画可能"飞"到错的位置。

**缓解**：
- 落点 ③ 在 v1 标记为"可选"，先做 ① ② 两个稳的。
- 真做时用 Motion 的 `layoutScroll` + `layoutDependency` 控制测量时机。
- 出问题就降级为 `AnimatePresence` 单纯淡入淡出。

---

### R3 · 装饰层 SVG 在长时间运行下 GPU 占用上升

**现象**：Background Beams 的 SVG 持续动画在 macOS Activity Monitor 里能看到 GPU 5%~10% 持续占用。

**影响**：电池续航下降；用户长时间挂着会发热。

**缓解**：
- Beams 只在 EmptyState 出现，dock 有 panel 时 unmount。
- 监听 `document.visibilityState === 'hidden'` → 暂停 SVG 动画。
- prefers-reduced-motion / 低电量模式下退化为静态渐变。

---

### R4 · React 19 与 Motion 的并发渲染兼容性

**现象**：Motion 的 layout 测量阶段在 React 19 自动 batching 下偶发 1 帧错位（社区已有 issue）。

**影响**：tab 切换瞬间 indicator 可能跳一下。

**缓解**：
- 锁 motion 到当前最新稳定版（cargo 锁版本）。
- M3 验收必须在 React 19 + Motion 当前版下手动验"切 100 次 tab 0 跳变"。
- 出 issue 时降到 React 18.3 是兜底方案（不到万不得已不动）。

---

### R5 · layout.json schema 演进

**现象**：未来加新 panel / 改 group 类型 → 老的 `layout.json` 反序列化失败。

**影响**：用户重启后布局丢失，体验差。

**缓解**：
- JSON 顶层带 `version`，写 migration 函数。
- 解析失败永远落回 `defaultLayout`，不抛异常。
- 升级时把旧 `layout.json` 备份成 `layout.v1.json` 留作 debug。

---

### R6 · `fs.watch` 在 macOS / Linux 上的递归限制

**现象**：Node 的 `fs.watch({ recursive: true })` 在 Linux 不支持(只能逐层注册);macOS / Windows 支持但大目录(>50k 文件)会丢事件。

**影响**：资源管理器在外部修改后未能即时刷新树。

**缓解**：
- MVP 直接用 `recursive: true`,信任 macOS / Windows 行为。
- Linux 用户(后续)走 chokidar fallback,通过 feature flag 切换。
- `useFsWatcher` 设计成"事件驱动 invalidate",即便丢事件,用户切换树节点时也会重新拉。

---

### R7 · 无 IPC 沙箱(VSCode 风权限)的安全风险

**现象**:`08-资源管理器方案.md` 决定不做 home 边界 / 敏感目录黑名单,理论上 main 进程的 `fs.*` 能写 `/etc`。

**影响**:用户(或后续接入的 Agent)可能误删/误改系统文件。

**缓解**:
- preload 入参用 zod 校验类型,但**不做路径白名单**(否则就不"VSCode 风"了)。
- 危险操作(remove)在 renderer 必须走 React 确认对话框。
- 默认 `remove` 走系统回收站(`shell.trashItem`),用户主动选"永久删除"才硬删。
- Nous Agent 联动时(未来里程碑),给 Agent 工具调用单独加一层路径白名单 / 二次确认,在 `IAgentShell.filesystem` 适配器里实现,**不污染本层**。

---

### R8 · headless-tree 不自带虚拟滚动 → 集成胶水成本

**现象**:`tree.getItems()` 返回扁平已展开节点数组,需要手动接 `@tanstack/react-virtual` 才能渲染万级节点。

**影响**:首次接入需写 ~30 行集成代码;若写错则大目录卡顿。

**缓解**:
- 参考 `examples/headless-tree/packages/sb-react/src/scalability/virtualization.stories.tsx` 的官方示例。
- 包成 `<VirtualTree>` 组件,`FolderTree.tsx` 不写虚拟滚动细节。
- 单测覆盖"5000 节点滚动 60fps"作为回归门槛。

---

### R9 · Zustand vanilla store 在 React 19 严格模式下的双订阅

**现象**:React 19 StrictMode 会双调 `useSyncExternalStore` 的 subscribe 函数,vanilla 实现需保证 unsubscribe 幂等。

**影响**:开发模式下出现重复订阅或内存泄漏假象。

**缓解**:
- `closing-store.ts` 已是 vanilla 风格,本项目所有新 store 沿用同模式。
- 单测覆盖"订阅-取消-再订阅"路径。
- StrictMode 在开发期保留(暴露问题),生产构建自动剥离。

---

## ADR 记录

### ADR-001 · 选 Dockview 而不是 Allotment

- **背景**：两者都派生自 VSCode 源码。
- **决策**：选 Dockview。
- **理由**：Dockview 内建 popout API + tab dock，Allotment 只做分栏。我们规划里"拖出独立窗口"是核心卖点，Allotment 实现成本远高于 Dockview。
- **不选的代价**：Dockview 的 API 比 Allotment 复杂，学习曲线略陡。

### ADR-002 · 装饰组件复制源码而非装包

- **背景**：Aceternity / Magic UI 都提供 npm 包。
- **决策**：复制源码。
- **理由**：(1) 官方文档就是 copy-paste 工作流；(2) 复制后能删冗余 props 减体积；(3) 不被外部包版本绑定。
- **不选的代价**：未来升级 Aceternity 时要手动 diff，但反正只用 2 个组件。

### ADR-003 · 不引入 tRPC / electron-store

- **背景**：Electron IPC 通道才 3 个，state store 也只是 layout.json。
- **决策**：手写 zod-validated ipcMain.handle + fs/promises。
- **理由**：复杂度远小于上 tRPC / electron-store 的边际收益。
- **不选的代价**：通道增多到 ~10 个时再考虑迁移。

### ADR-004 · Tab indicator 用 spring，PanelMount 用 ease-out tween

- **背景**：两者节奏感不同，spring 更"弹"，tween 更"滑"。
- **决策**：indicator = spring（stiffness 500 / damping 35），PanelMount = tween 220ms ease。
- **理由**：indicator 是高频小元素，spring 的快速到位 + 微震尾感觉灵敏；PanelMount 是大块进出场，spring 会显得轻浮，tween 更稳。
- **不选的代价**：两套 transition 配置需要在代码里维护两份。

### ADR-005 · 资源管理器树选 `headless-tree` 而非 `react-arborist`

- **背景**:候选有 react-arborist(全包式、内置虚拟滚动、11.5k★)和 headless-tree(纯逻辑库、Feature 插件化、3.5k★)。
- **决策**:选 headless-tree + `@tanstack/react-virtual`。
- **理由**:(1) 异步 dataLoader 与 IPC 调用是天作之合,内置去重/缓存/单节点 invalidate;(2) headless 架构与 motion / Tailwind 0 摩擦,未来接入展开动画无阻;(3) Bundle 小 25KB+,Feature 按需启用契合"渐进 MVP"。
- **不选的代价**:虚拟滚动需自己接 ~30 行胶水(可接受);右键菜单和搜索框 UI 需自写(本来也要)。

### ADR-006 · 资源管理器路径权限走 VSCode 风(无 IPC 沙箱)

- **背景**:候选有 (A) 完全无限制、(B) Nous 风 home 沙箱、(C) MindAutonAgent 风 home + 黑名单 + 符号链接检查。
- **决策**:选 VSCode 风 — 无 IPC 沙箱,通过 workspace root 概念 + UX 确认弹窗约束行为。
- **理由**:(1) 用户明确要"任意目录"开发体验,home 限制反而碍事;(2) 信任 OS 文件权限,不重复造防御;(3) 与 VSCode 习惯一致,降低用户心智成本。
- **不选的代价**:无应用层防护,误操作风险更高 → 用回收站 + 确认对话框兜底(见 R7);Nous Agent 联动时需在 `IAgentShell.filesystem` 适配层单独加白名单。

### ADR-007 · 状态库继续 Zustand,vanilla 化

- **背景**:LayoutMotion 已用 `zustand@5.0.2`(`closing-store.ts`),但用 React hook 风;Nous CLI 用 `zustand/vanilla` + `useSyncExternalStore`。
- **决策**:沿用 Zustand,新 store 全部走 vanilla 模式,顶层化到 `src/stores/`,旧 `closing-store.ts` 一并迁移。
- **理由**:(1) 与 Nous CLI shell 同款,联动时 store 可跨主/渲染进程复用;(2) vanilla store 不强绑 React,便于将来给 preload / 主进程订阅;(3) 体积仍是 ~2KB,符合极简原则。
- **不选的代价**:比 hook 风稍多一行 `useSyncExternalStore` 模板;StrictMode 双订阅需注意幂等(见 R9)。

### ADR-008 · 资源管理器 MVP 不接节点展开 motion 动画

- **背景**:headless-tree 的 row 可包 `<AnimatePresence>` 做展开过渡,但需处理虚拟滚动测量时机。
- **决策**:MVP 不接,先稳定虚拟滚动 + IPC 数据流 + UX 完整度。
- **理由**:(1) 极简优先,动画是叠加项不是核心价值;(2) 虚拟滚动下 motion 测量与 react-virtual translate 易冲突,延后到验证完性能后再加;(3) `MotionConfig reducedMotion="user"` 已在 shell 层生效,后续补回不破坏现有结构。
- **不选的代价**:展开/折叠视觉略平,但树本身已有 indent 与图标识别,不影响可用性。

### ADR-009 · `fs:write` 走原子写(temp + fsync + rename)

- **背景**:候选有 (A) `fs.promises.writeFile` 直接覆写、(B) Lokus 风原子写(写 tmp → fsync → rename → cleanup backup)。
- **决策**:选 B,所有写文件路径(`writeFile` / `createFile`)统一走原子写。
- **理由**:(1) 编辑器场景常见进程崩溃 / 断电,直接覆写有半写损坏风险;(2) `rename` 是 POSIX 原子操作,崩溃只会留下 `.tmp` 或原文件其一,数据永不丢;(3) 纯 `fs.promises` 实现,不引入新依赖;(4) 资源管理器 MVP 即使没编辑器,createFile 也受益。
- **不选的代价**:每次写多 1 次 fsync + 1 次 rename,小文件 < 5ms 开销,可忽略;`.tmp` / `.backup` 残留需 cleanup 兜底逻辑。
- **参考**:`examples/lokus/src-tauri/src/handlers/files.rs` 的 `atomic_write_file`。

### ADR-010 · 全工程 IPC 通道走 `safeHandle` + `IpcResult<T>`

- **背景**:Electron 官方 security 第 17 条要求 IPC handler 校验 `event.senderFrame`,2025 年多个 CVE(GHSA-mq8j-3h7h-p8g7)源于此;现有 `electron/main/ipc.ts` 三个 handler 不校验 sender,且 `layout:write` 把异常吞成 `false`,renderer 拿不到失败原因。
- **决策**:封装 `safeHandle(channel, schema, handler)`,内部按顺序做 ① `event.senderFrame` origin 校验 → ② `zod.parse` 入参 → ③ 调 handler → ④ 包成 `IpcResult<T>`(成功 `{ok:true, data}` / 失败 `{ok:false, code, message}`)返回。`layout:*` 与 `fs:*` 全工程通道一律使用此 envelope,无例外。
- **理由**:(1) 满足 Electron 2025 安全清单第 17 条,关闭 popout 子 frame 的 IPC 横向越权面;(2) 错误结构化,renderer 端可按 `code` 差异化处理(权限不足 → 弹确认 / 路径不存在 → 重新刷新 / IO 错 → toast);(3) 一处封装,所有通道复用,新增 fs.* 通道时 0 心智成本;(4) zod 校验与原有规范一致,只是再下沉一层。
- **不选的代价**:现有 `layout:write` 返回 `boolean` 的调用方(`src/shell/dock/DockShell.tsx`)需改一行为 `result.ok`;新增 `IpcResult` 类型放 `src/lib/fs/types.ts` 共享(虽然名字带 fs,但语义是全工程的 IPC envelope,后续可考虑改名 `src/lib/ipc/result.ts`)。
- **配套行动**:文档 `doc/05-Electron-集成.md` § main 侧 IPC 示例代码本里程碑期间一并更新到 safeHandle 风格。

### ADR-012 · 资源管理器持久化字段范围(VSCode 风)

- **背景**:Step 3 选 c 方案(扩展 `userData/explorer.json` + `explorer:read/write` IPC,与 `layout.json` 同模式)。需要决定哪些 store 字段进入持久化文件、哪些只在内存。
- **决策**:VSCode 风。持久化 = 用户配置 + 树状态 + 焦点 + Pin;**不持久化** = 瞬时交互态。
  - ✅ `workspace.root` / `workspace.recentRoots`
  - ✅ `explorer.expandedPaths` / `explorer.activePath` / `explorer.sort`
  - ✅ `pinned.paths`
  - ❌ `explorer.selectedPaths`(多选,只在当前会话有意义)
  - ❌ `explorer.lastAnchorPath`(仅 Shift+click 范围选用)
  - ❌ `explorer.search`(搜索串重启清空,VSCode 同行为)
- **理由**:(1) `activePath`(焦点)持久化提升体验,VSCode 重启后还会回到上次的文件;(2) 多选/搜索是"当前手势"产物,持久化反而让重启后陌生 UI 状态卡在用户脸上;(3) 减小 explorer.json 体积与写频率(瞬时态高频变化,过滤后 debounce write 触发更少)。
- **不选的代价**:hydrate 时需显式复位瞬时字段(已在 `hydrateStores` 实现);若用户期望"恢复多选会话"需求(罕见),需重新讨论。
- **数据形态**:磁盘 JSON 全用 array(JSON 不支持 Set),store 内部 `expandedPaths` / `selectedPaths` 用 Set;`snapshotFromStores` / `hydrateStores` 负责互转。
- **持久化层位置**:`src/lib/persist/explorer-persist.ts`,`initExplorerPersistence(api)` 在 App 启动调用,debounce 300ms 写(沿用 DockShell 的 layout debounce 节奏)。

### ADR-011 · 升级 Electron 33 → 38

- **背景**:`package.json` 锁 `electron: ^33.2.1`,Electron 33 已于 2025 中过 EOL;2025 全年披露的 5 个 sandbox 逃逸 / context 隔离绕过补丁不会回种到 33。
- **决策**:升级到 Electron 38(LTS-window 内长支持轨)。不直接跳 39 是为求稳;38→39 留作下一个安全窗口期。
- **理由**:(1) 33 已 EOL,继续用等于带漏洞跑生产;(2) 38 是 6 个月长支持轨,过 EOL 时间最长,最不需要频繁追版本;(3) 与 React 19 + Vite 5 + electron-vite 2 + dockview-react 4 全部兼容,实测无破坏性 API 改动;(4) 我们用的核心 API(`BrowserWindow / contextBridge / ipcMain.handle / shell.openExternal`)从 v20 起稳定,不受跨版本影响。
- **不选的代价**:Chromium 版本一并升级,renderer 行为可能有微差(`prefers-reduced-motion` / GPU 调度等);需要在升级后回归测一次"切 100 次 tab 0 跳变"(M3 验收项)。
- **配套行动**:升级落地后,`doc/00-计划书总览.md` 技术选型表"桌面壳"行注明 Electron 38+。
